kepler · the workspace manager

What Kepler does for you

One machine, many projects, one attention span. Kepler is the operating layer that keeps a whole fleet of AI-driven projects findable, resumable, and honest about their state — so no project dies of being forgotten.

This is the workspace half of a two-product story. The other half — gravity, the doc protocol each project adopts — has its own guide: gravity/GRAVITY-GUIDE.html, the page that travels into every project as .gravity/GRAVITY.html.

01Two products, one workspace

What lives here is two things with one repo between them, and keeping them apart is what makes either work:

Kepler this machine

The workspace manager — the laws of motion for a fleet of projects: tiers, junctions, the live index, the dashboard, the weekly drift survey. It never leaves this root, and it is deliberately unversioned — git history is its changelog.

gravity travels

The protocol a project adopts — doc kinds, domain rules, SPEC walls, evidence doors, instruments. SemVer'd apart (gravity/VERSION + tags), shipped whole inside each independent repo, working with no workspace in sight.

The split rule that decides where anything belongs: if a cloned project repo could need it, it's gravity; if only this machine's portfolio needs it, it's Kepler. That one test is why gravity can be versioned, released, and adopted elsewhere while Kepler stays a private operating layer.

02The problem it solves

Working with coding agents makes starting projects nearly free — and that is exactly the trap. The fleet grows faster than your attention, and three things start dying quietly:

  • Findability — "where did I put that, and which copy is real?" Folders multiply across drives; two half-versions of the same idea drift apart.
  • Resumability — "what was I doing, and what's next?" A project untouched for six weeks costs an evening of archaeology before any real work.
  • Honesty of state — "is this paused, shipped, or dead?" Without a place to say so, everything silently becomes the same thing: old.

Kepler's answer is structural, not motivational: real files live in exactly one place, every project sits in exactly one lifecycle tier, one index lists them all, and a weekly mechanical survey names what's drifting. Nothing relies on you remembering.

03Storage & views — repos and junctions

The load-bearing trick is separating where files live from how they're organized. Real project files live once, in repos/. The tier folders hold directory junctions — filesystem pointers — so a project's tier is a view, not a location.

A project appears in exactly one tier at a time — the figure shows the four possible views onto one canonical folder.

Two consequences make this worth the setup:

  • A tier move is instant. mv stable/orbit active/ re-points one junction — metadata only, never a copy, never touching node_modules or .venv.
  • Git sees through junctions. Commands run inside active/orbit operate on the real .git in repos/orbit — each project stays its own independent repo with its own remote.
The one hard invariant. Tier folders hold junctions only — never real files. An existing repo elsewhere (another drive, a path an IDE hardcodes) joins by junctioning straight from the tier folder to its external path; the files never move. And links are created only via python .claude/scripts/link_project.py — argv-driven, so no shell quoting bug can silently create a broken link.

04The lifecycle — four tiers, one reading

The tiers read as a sentence: being worked · works · paused · over. Every transition is one move plus one honest line in the project's CONTEXT.md:

Three tier meanings carry more weight than they look:

  • stable/ is not "old active". Shipped and in use, nothing in flight — so staleness rules don't apply there. Its CONTEXT.md names the reactivation trigger: "back to active when X". Silence is success, not neglect.
  • dormant/ requires a named blocker. That's what separates paused from abandoned: something specific blocks it, written down, so resuming starts from the blocker rather than from archaeology.
  • There is no incubator tier. An idea goes straight to active/; if it dies within days, /retire and delete. A cheap "someday" tier just becomes a graveyard with better branding.

05The index & the session ritual

PROJECTS.md is the fleet's one index — one row per project: name, stack, last touched, and a tier-appropriate one-liner (focus · reactivation trigger · resume blocker). It's local-only and git-ignored, because it names private work; the skeleton ships a sanitized sample. Every tier transition updates it, and the mechanical checks compare it against reality so it can't quietly rot.

Every project keeps two root files, whatever else it adopts: CLAUDE.md (stable identity — stack, run/test, gotchas; auto-loads for agents) and CONTEXT.md (a rolling snapshot of now: Completed / Current State / Next Step). The session ritual is symmetric: read CONTEXT.md first, update it before you stop. A session that ends without updating it is incomplete — that update is what makes the next resume free.

Snapshot, not log. CONTEXT.md stays small by rule: Completed keeps only the last session or two, Next Step is exactly one item, and pruning is non-destructive because git log -p holds every past version. /triage flags files that outgrow the thresholds.

06The protocol, in one screen

Everything in this section travels inside the project repo — it keeps working in a clone that has never seen this workspace. One line each; the full treatment, with diagrams and its own phrasebook, is the gravity guide.

The ruleIn one line
Four clocksDocs split by rate of change — mission (rarely) · CLAUDE.md (on refactors) · plan (per phase) · CONTEXT.md (per session). Mixing rates is what makes docs rot.
One concern, one homeEvery fact has one owner-doc; everything else links to it. The same fact written twice eventually becomes two different facts.
Domains, not doc-typesHeavy docs live in .gravity/<domain>/, one folder per subject; a leading _ marks gravity's own machinery, never a domain.
SPECs are wallsA Minimal Shape to build from, plus Rules that fence it — every rule tagged with what actually enforces it, or honestly tagged that nothing does.
Direction earns a homeA principle becomes a Track, a Track becomes slices, slices leave residue as SPEC rules — and then the Track retires.
Three evidence doorsBug reports (the past), handed-in knowledge, and agreed requirements (the future) enter as cited text before anything is planned.
Brownfield inverts the orderOn a system you didn't write, integration comes first: a Boundary Map where every row cites its source, and an untraceable seam stays an honest OPEN:.

And it's versioned. gravity follows SemVer as a convention system — major = a rule projects depend on breaks — with the version in gravity/VERSION + a git tag, never in prose. Each adopted project carries a version stamp, so a stale adoption is visible (📡 in /triage, chips on the dashboard) and repairable (/sync-gravity). Kepler itself is deliberately unversioned — nothing adopts it, so nothing can be stale against it.

08What is checked mechanically

Kepler's claims are cheap to make and expensive to keep true by hand — so the keeping-true is mechanical. Stated narrowly, like everything else here:

The same reading as the protocol side: green means the bookkeeping is intact, never the portfolio decisions are right. What to work on stays your call — Kepler just guarantees the question is asked over true data.

09What Kepler does not do

  • It is not a backup. repos/ is canonical storage, not redundancy — each project's own git remote is its safety net, and Kepler deliberately stays out of that.
  • It never becomes the umbrella repo. The skeleton repo's .gitignore is deny-all-then-whitelist: tier folders cannot be committed here. Your projects' history stays theirs.
  • It keeps no cloud or cross-machine state. PROJECTS.md is local-only by design (it names private work). A sibling workspace on another drive is updated by /deploy-kepler — a manifest copy of the skeleton, never of project state.
  • It doesn't version itself. Only gravity carries a version, because only gravity is adopted — a version exists to detect stale adoptions, and nothing adopts Kepler.
  • It doesn't nag what's healthy. stable/ is exempt from staleness by definition, and no mechanism pushes you to "do something" with a shipped project. The pressure Kepler applies is honesty about state, not activity.

10The philosophy, and where to go next

  • Weaker-agent walls. Wherever judgment can fail, build a mechanical wall instead: argv-driven scripts, verbatim copies, versions that are read and never invented. A less capable agent can't fabricate enforcement — and a more capable one doesn't have to be trusted.
  • Honesty over completeness. An unknown is an OPEN: line, not a plausible guess. A paused project names its blocker. A partial state is a valid state, said plainly.
  • Ceremony must pay. Two docs are the minimum and often the maximum. Every structure here is recognized only when present, and deleted when it stops earning its keep.
  • Intent is the scarce resource. Models get stronger and code gets cheaper; your decisions, non-goals, and boundaries do not regenerate. The whole system exists to make those durable — and to apply them to work you'll never personally watch.
