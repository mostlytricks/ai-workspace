# DESIGN.docs — the browser-read doc theme

The look of gravity's **human-facing HTML docs**: `MISSION.html`, `ARCHITECTURE.html`, and any
page you hand-roll to be read in a browser. Deep-navy glass by default, five interchangeable
palettes, zero runtime dependencies — no CDN, no `@font-face` — so a doc still renders from
`file://` on a plane.

> **This file explains. It does not define.**
> The stylesheet is **generated** by [`gravity/lib/doc_theme.py`](lib/doc_theme.py). There is no
> stylesheet to paste here, on purpose — see *Why this moved* below.

**Applies to:** browser-read HTML docs.
**Does not apply to:** Markdown docs (`CLAUDE.md`, `CONTEXT.md`, `IMPLEMENTATION_PLAN.md`,
`SPEC.md`) — they render wherever the agent reads them; the **running app's** visual identity —
that's the project's own `DESIGN.md` (`templates/DESIGN.template.md`), a different concern that a
project may also have; and the **observatory**, which is generated by
`lib/generate_observatory.py` and owns its own chrome.

---

## Why this moved (and why it's code now)

This file used to live at `docs/DESIGN.docs.md` and carry a full stylesheet you were meant to
copy. Both facts were bugs, and they compounded:

1. **It lived on the wrong side of the split.** `docs/` is Kepler — the workspace manager, this
   machine only. The templates it themed live in `gravity/`, which travels into independent
   repos. Every generated doc carried a header line saying *"see docs/DESIGN.docs.md in the
   workspace"* — a pointer that dangles in every clone, i.e. in exactly the place the doc gets
   read. A theme nobody can reach is a theme nobody follows.
2. **A pasted stylesheet has no inverse.** When the five-theme switcher arrived, the tooling
   *appended* an override block rather than replacing the sheet. Every doc ended up with two
   `:root` blocks — roughly ninety lines of dead tokens shadowed by the ones below them — and
   this file went on documenting the dead half. New projects copied the scar from the stencils.

So the sheet became a function, and the function lives in `lib/` where `install_lib.py` already
copies it into every project's `.gravity/_lib/`. A clone that has never seen this workspace can
regenerate its own doc CSS.

## The three files that own this

| File | Owns | Changes when |
|---|---|---|
| [`lib/palette.py`](lib/palette.py) | the **anchor hues** — chrome (`bg`/`ink`/`dim`/`h1_grad`) and status (`accent`/`ok`/`plan`/`guard`/`sat`) for all five themes | a hue is retuned |
| [`lib/doc_theme.py`](lib/doc_theme.py) | the **stylesheet** — layout, type, glass treatment, status classes, the flow-diagram (`fd-`) vocabulary, the switcher | the docs' *look* changes |
| `.kepler/scripts/apply_doc_theme.py` | **applying** it to real files (workspace-side; not part of the protocol) | never, ideally |

Anything not in that table — panel translucency, hairline weights, blur radius, the ambient glow
geometry — is **docs-local** and lives in `doc_theme.CHROME`. It's how a *reading* surface differs
from a *scanning* one, and nothing cross-checks it because nothing else draws it.

**The rule:** retune a hue in `palette.py` **first**, then propagate. `check.py theme` FAILs on
disagreement (`THEME_DRIFT`, `STATUS_DRIFT`), so a partial edit can't pass quietly.

## The five themes

One family, one `localStorage` key (`dash-theme`) shared with the dashboard and the observatory —
pick a theme anywhere, it applies everywhere.

| Theme | Mood | `bg` / `accent` |
|---|---|---|
| **`aurora`** (default) | deep-navy neon glass | `#0A0E1A` / `#00E5E8` |
| **`daylight`** | clean light, blue-violet | `#F7F9FC` / `#2563EB` |
| **`sandstone`** | warm paper, terracotta | `#FBF6EF` / `#C2410C` |
| **`forest`** | dark green | `#0C1A14` / `#34D399` |
| **`slate`** | neutral graphite | `#16181D` / `#94A3B8` |

Switching re-points every `var(--token)` already in use; the flourishes (ambient background,
gradient `h1`, logo glow, glass shadow, card hover) are **tokenized**, not gated, so the light
themes get a fitting treatment rather than a dimmed dark one.

## Structural vocabulary

Layout and reading furniture:

- `.wrap` — 920px centred column · `header.top` + `.logo .sq` + gradient `h1` + `.lede`
- `h2 > span.n` — monospace section number (`01`, `02`, …)
- `.toc` — boxed two-column glass contents
- `.cards` → `.card` (+ `.pill.live` / `.pill.mock`) · `.phase` (+ `.tag.done` / `.next` / `.todo`)
- `.note` (+ `.warn`, `.red`) — left-bordered callout; `.lbl` for the lead-in
- `pre` — glass code block, for genuinely textual content only (code, config, directory trees — never a figure; figures are `fd-` SVG); inside it `<b>`, `.c` (comment), `.a` (accent), `.b` (blue)
- `table`, `footer`

## Flow-diagram vocabulary — inline SVG

**Figures are SVG.** Any architecture drawing — the system page's §01 glance map, any flow with
branches, fan-in or parallel paths — is **hand-authored inline SVG**: never ASCII art in a `pre`
(a `pre` sketch reads no theme token, anchors no `data-path`, and a walkthrough's delta figure
can't echo it), and never an external JS diagram library. A strictly *linear* trace may stay a
`.flow` ordered list — it's HTML, so it wraps and its `<code>` cells anchor; `pre` is for
genuinely textual content (code, config, directory trees), not figures. The SVG rules are the
theme's own three rules applied to vectors:

1. **No CDN, no scripts.** Same rule as fonts: a doc opened from `file://` on a plane still
   renders. Inline SVG is part of the document; mermaid/d3 from a CDN is a trust and availability
   dependency the docs must not carry.
2. **Themable by construction.** Every stroke and fill reads a token (`--card`, `--line`,
   `--text-mid`, `--blue`, `--red`), so the switcher restyles diagrams with the page — a
   hardcoded hex in an SVG is drift the five palettes can't reach.
3. **Checkable like the grid.** Put `data-path="server/src/x.ts"` on a node's element —
   `check.py arch`'s extraction is a raw-text regex and element-agnostic, so SVG nodes are
   validated exactly like `<code data-path>` cells. (Caveat: only ARCHITECTURE pages are
   scanned — an anchored flow belongs there, not in MISSION.html.)

| Class | On | Means |
|---|---|---|
| `.fd` | the `<svg>` | a flow figure; author with a `viewBox`, it scales to the column |
| `.fd-node` | `rect` | a step — card fill, line stroke |
| `.fd-edge` | `path`/`line` | an arrow that exists |
| `.fd-seam` | an edge or node | crosses a runtime boundary (the `.flow` list's `li.seam`) |
| `.fd-gap` | an edge | does **not** exist yet — red *and* dashed, never hue alone |
| `.fd-new` | a node or edge | added/changed **by this slice** (walkthrough figures) — accent *and* heavier stroke |
| `.fd-old` | a node or edge | removed by this slice — faint *and* dashed |
| `.fd-label` / `.fd-file` | `text` | step name / the anchored file path (mono) |
| `.fd-arrow` | the marker's `path` | arrowhead — one neutral hue (markers don't inherit edge stroke cross-browser) |

Boundaries that keep it honest: **one flow per figure, ~12 nodes max** — SVG text does not wrap,
so anything tabular stays an HTML grid (`.grid`) and anything longer gets split or stays a
`.flow` list. Each figure carries its own `<defs>` with a **unique marker id** (two figures on one
page sharing `#fdarr` is a duplicate DOM id — browsers silently resolve to the first, so the
breakage would be invisible; suffix the id with the flow's slug):

```html
<svg class="fd" viewBox="0 0 720 120" role="img" aria-label="request flow">
  <defs><marker id="fdarr" viewBox="0 0 8 8" refX="7" refY="4" markerWidth="7"
    markerHeight="7" orient="auto"><path class="fd-arrow" d="M0 0L8 4L0 8z"/></marker></defs>
  <rect class="fd-node" x="8" y="30" width="150" height="52" rx="10"/>
  <text class="fd-label" x="24" y="52">route</text>
  <text class="fd-file" x="24" y="70" data-path="server/src/index.ts">server/src/index.ts</text>
  <line class="fd-edge" x1="158" y1="56" x2="230" y2="56" marker-end="url(#fdarr)"/>
  <!-- … next node … -->
</svg>
```

The classes are `fd-`-prefixed for the same reason the legend strip is `.marklegend`, not
`.legend`: `.flow`, `.node`, `.trace`, `.grid` and `.legend` are per-doc template classes, and
`apply_doc_theme.py` deletes any per-doc rule whose selectors the generator claims as its own.

## Status vocabulary — shared with the observatory

The docs and the observatory describe the same project. When one says *"this is proven"* and the
other says *"this is a wall"*, they should not invent separate looks for it — so the observatory's
marks are available in authored docs, restyled for a reading column.

| Class | Means |
|---|---|
| `.mark.m-live` ◑ | live / in flight |
| `.mark.m-ok` ✓ | proven |
| `.mark.m-plan` ○ | planned |
| `.mark.m-guard` ▲ | a wall, or drift |
| `.pchip.pok` / `.pwarn` / `.pbad` / `.pnone` | the recorded outcome of a check |
| `.ocard` (+ `.warn`, `.ok`), `.ohead`, `.okv`, `.olbl` | a claim that needs a heading and a body |
| `.vd` (+ `.vok`, `.vbad`, `.vwarn`, `.vneutral`) | the one-sentence verdict strip |
| `.marklegend` | the strip that explains the marks used on this page |

Three rules that make these honest rather than decorative:

1. **A mark is a claim, not a decoration.** `.pchip.pok` asserts a human checked it on a date.
   `.pchip.pnone` asserts nobody has — which is why it renders *dashed*. Absence of proof must
   never look like proof.
2. **Never colour alone.** Every mark carries a glyph *and* a hue. A bare colour is the one
   encoding a colour-blind reader cannot resolve.
3. **Don't upgrade a chip because a checker passed.** `check.py arch` proves a `data-path` still
   resolves to a real file. It cannot tell you the arrow is right or that an undrawn branch was
   added. Say which is which.

**Naming note:** the strip is `.marklegend`, not `.legend`. The ARCHITECTURE grid pages already
own `.legend` for their cell-state key, and silently restyling it would be precisely the drift
this generator exists to stop.

The status tokens are emitted as `--st-live` / `--st-ok` / `--st-plan` / `--st-guard` /
`--st-sat`. The prefix isn't cosmetic: the docs already had an `--accent` meaning *"link"*, and in
`forest`, `slate` and `sandstone` that hue collides with a *different* status hue. Reusing the
bare names would have given every hyperlink a status meaning.

## Using it

**New doc** — copy a stencil (`templates/MISSION.template.html`,
`templates/ARCHITECTURE.template.html`, `templates/ARCHITECTURE.domain.template.html`). Each ships
the current generated theme and the switcher.

**Hand-rolled page** — generate the block and paste it:

```bash
python gravity/lib/doc_theme.py            # the whole <style> element
python gravity/lib/doc_theme.py --parts    # head init · themebar · switcher script
```

**After changing the theme** — regenerate every doc in place:

```bash
python .kepler/scripts/apply_doc_theme.py                    # dry run, everything
python .kepler/scripts/apply_doc_theme.py --skeleton          # stencils only, no repo touched
python .kepler/scripts/apply_doc_theme.py <project> --apply   # write one project
```

Dry run is the **default**; nothing is written without `--apply`.

**Your custom CSS is safe.** The script replaces only the fenced
`/* gravity:doc-theme BEGIN … END */` block and drops base rules the generator now provides. A
rule whose selector the generator does *not* define is kept verbatim, moved below the generated
block so it still wins, under a `per-doc CSS` banner. That matters: the ARCHITECTURE pages carry
30–45 custom selectors each — grid cells, trace lanes, node markers — and losing them would wreck
the exact docs this exists to improve.

**Verify:**

```bash
python gravity/lib/doc_theme.py --self-test   # the generated CSS carries every anchor
python .kepler/scenarios/check.py theme       # all surfaces agree, chrome and status
```

## Relationship to the other themed surfaces

Three surfaces draw the same five palettes in **three deliberately different token vocabularies** —
they are different surfaces, not duplicates, and `palette.py` maps between them rather than
merging them:

| Surface | Built for | Token names | Drawn by |
|---|---|---|---|
| **docs** (this) | reading | `--panel` · `--text-hi` · `--st-ok` | `lib/doc_theme.py` |
| **observatory** | instrument density | `--card` · `--ink` · `--ok` | `lib/generate_observatory.py` |
| **dashboard** | scanning the fleet | `--surface` · `--ink` · `--muted` | `.kepler/dashboard/generate_dashboard.py` |

The dashboard vendors Outfit/Inter/Fira Code and Chart.js and animates; docs fall back to the
system stack and stay still. When you restyle one, decide deliberately whether the others follow —
then let `check.py theme` hold you to it.
